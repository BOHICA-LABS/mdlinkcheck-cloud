# S-2.03: Code Context Exclusion and Anchor Table Integrity for Fenced Code Blocks

> **One-per-file:** This story is `S-2.03` in EPIC-02 — Link Extraction and Code Context Exclusion (`E-2`).
> Verifies that `link_extractor::extract` never extracts links from fenced code blocks, tilde
> fences, inline code spans, 4-space indented code blocks, or HTML comment content (DI-004).
> Additionally verifies the cross-module BC-2.04.003 guarantee: `anchor_table::build` must
> produce zero anchor entries for heading-like lines (`# Title`) that appear inside fenced code
> blocks. Both modules are tested independently with dedicated unit tests per BC-2.04.003
> story-writer routing note (SF-003).

> **Cross-module note:** BC-2.04.003 has joint ownership: `link_extractor` (SS-04) and
> `anchor_table` (SS-05). The `anchor_table` side is also in scope for EPIC-03, but the
> combined exclusion guarantee must be verified here as a unit. The story does NOT implement
> `anchor_table::build`'s heading-extraction logic (that belongs to EPIC-03 S-3.xx) — it
> verifies that the pulldown-cmark structural guarantee (no `Tag::Heading` inside `Tag::CodeBlock`)
> holds, using a dedicated unit test on `anchor_table::build` directly.

## Narrative

- **As a** developer running `mdlinkcheck` on a Markdown repository with code examples
- **I want** links written inside code blocks, inline code spans, indented blocks, and HTML
  comments to be completely ignored
- **So that** code snippets demonstrating broken or example link syntax never produce false
  positive findings, and fake headings inside code fences never pollute the anchor table

| BC-2.04.002 | Indented Code Blocks and HTML Comments Yield No Links | P0 |

## Acceptance Criteria

> **Verification Properties:** VP-014 (code-context exclusion integration test — DI-004: no link
> inside any code context is ever extracted) applies to all three BCs in this story and is
> referenced in frontmatter per VP-INDEX v1.7. VP-014 covers the `link_extractor` side.
> BC-2.04.003's `anchor_table` side has no current VP (VP-NONE per BC-2.04.003 v1.5); the
> test-writer MUST add a dedicated integration test `test_BC_2_04_003_anchor_table_build_no_entry_for_fenced_heading()`.
> This gap is recorded here — admitting it is the correct outcome per constraint 11.

### AC-001 (traces to BC-2.04.001 postcondition 1)
`link_extractor::extract` returns zero `ExtractedLink` entries for any Markdown content that
exists inside a backtick-fenced code block (` ``` `). A file whose entire content is a fenced
block containing `[x](missing.md)` exits 0 with no findings.
- **Test:** `test_BC_2_04_001_fenced_code_block_yields_no_extracted_links()`

### AC-002 (traces to BC-2.04.001 postcondition 2)
`link_extractor::extract` returns zero `ExtractedLink` entries for any Markdown content that
exists inside an inline code span (`` `...` `` or ` `` ... `` `). A file containing only
`` `[x](missing.md)` `` exits 0 with no findings. Double-backtick spans are also excluded
(BC-2.04.001 invariant 2).
- **Test:** `test_BC_2_04_001_inline_code_span_yields_no_extracted_links()`

### AC-003 (traces to BC-2.04.001 postcondition 3)
The zero-extraction guarantee covers all fenced block variants: language-tagged fences
(` ```rust `), tilde fences (`~~~`), fences nested inside list items, and fences nested inside
blockquotes.
- **Test:** `test_BC_2_04_001_language_tagged_and_tilde_fences_yield_no_extracted_links()`
- **Test:** `test_BC_2_04_001_fence_inside_list_item_yields_no_extracted_links()`

### AC-004 (traces to BC-2.04.001 invariant 3)
An unclosed fenced code block (no closing ``` before EOF) consumes all content to EOF as
code block content (CommonMark behavior). Any `[x](missing.md)` after an unclosed opening
fence produces zero `ExtractedLink` entries.
- **Test:** `test_BC_2_04_001_unclosed_fence_at_eof_swallows_all_content()`

### AC-005 (traces to BC-2.04.001 invariant 1)
The exclusion is structural (AST event matching), not heuristic. `link_extractor::extract`
matches only `Tag::Link` and `Tag::Image` events. Code block content arrives as `Event::Text`
inside `Tag::CodeBlock` and `Event::Code` for inline spans — these event types never produce
`Tag::Link` events in pulldown-cmark. No explicit state-machine tracking of "inside code block"
is needed or permitted in `extract`.
- **Test:** `test_BC_2_04_001_exclusion_is_structural_not_heuristic()` (verify via code review
  that `extract` contains no explicit code-context tracking state variable)

### AC-006 (traces to BC-2.04.002 postcondition 1)
`link_extractor::extract` returns zero `ExtractedLink` entries for Markdown content inside a
4-space indented code block. A file containing `    [x](missing.md)` (four leading spaces)
exits 0 with no findings. Indented blocks are only recognized outside continuation contexts
(CommonMark rule, handled by pulldown-cmark correctly per BC-2.04.002 invariant 1).
- **Test:** `test_BC_2_04_002_four_space_indented_block_yields_no_extracted_links()`

### AC-007 (traces to BC-2.04.002 postcondition 2)
`link_extractor::extract` returns zero `ExtractedLink` entries for Markdown content inside an
HTML comment (`<!-- ... -->`). A file containing `<!-- [x](missing.md) -->` exits 0 with no
findings. HTML comments arrive as `Event::Html` / `Event::InlineHtml` containing `<!--`;
their content is not parsed as structured Markdown events (BC-2.04.002 invariant 2).
- **Test:** `test_BC_2_04_002_html_comment_content_yields_no_extracted_links()`

### AC-008 (traces to BC-2.04.002 postcondition 3)
`<pre>[x](missing.md)</pre>` and `<code>[x](missing.md)</code>` raw HTML elements yield
zero `ExtractedLink` entries. Raw HTML block content arrives as `Event::Html`, not as
structured Markdown link events.
- **Test:** `test_BC_2_04_002_pre_and_code_html_elements_yield_no_extracted_links()`

### AC-009 (traces to BC-2.04.003 postcondition 1 — link_extractor side)
A heading-like line (`# Fake Heading`) inside a fenced code block produces zero `ExtractedLink`
entries. The content is `Event::Text` inside `Tag::CodeBlock`, never a `Tag::Link` event.
This is covered by BC-2.04.001 and VP-014; recorded here for joint-ownership traceability.
- **Test:** `test_BC_2_04_003_heading_like_line_in_fenced_code_produces_no_link()`

### AC-010 (traces to BC-2.04.003 postcondition 2 — anchor_table side)
`anchor_table::build(events)` called with a `ParsedFile`'s events from a file whose only
heading-like content is inside a fenced code block produces an empty `AnchorTable`. pulldown-cmark
never emits `Tag::Heading` events for content inside `Tag::CodeBlock` — this is a structural
guarantee that must be verified with a dedicated unit test on `anchor_table::build` directly
(not only through the full integration pipeline). No anchor entry is created for the
heading-like line.
- **Test:** `test_BC_2_04_003_anchor_table_build_no_entry_for_fenced_heading()`
  (VP-NONE; integration test required — no current VP for anchor_table side per BC-2.04.003 v1.5)

### AC-011 (traces to BC-2.04.003 postcondition 3)
A link in the same file that references the slug of a heading-like line inside a fenced block
receives `broken(anchor-not-found)`. For EC-065: a file containing a fenced block with
`# Fake Heading` followed by `[x](#fake-heading)` exits 1 with verdict
`broken(anchor-not-found)` — because `# fake-heading` was never added to the anchor table.
- **Test:** `test_BC_2_04_003_ec065_link_to_fenced_heading_slug_yields_anchor_not_found()`

### AC-012 (traces to BC-2.04.003 invariant 1 and invariant 2)
pulldown-cmark's AST never emits `Tag::Heading` events for content inside `Tag::CodeBlock`.
This structural guarantee is the basis for both `link_extractor` and `anchor_table` correctness.
The unit test on `anchor_table::build` verifies the guarantee holds end-to-end: given events
from a parsed file with a fenced code block containing heading-like text, `build` sees no
`Tag::Heading` event and produces an empty table.
- **Test:** `test_BC_2_04_003_pulldown_cmark_emits_no_tag_heading_inside_tag_codeblock()`

| Module | Classification | Justification |
|--------|---------------|---------------|
| `link_extractor` | pure-core | Code context exclusion is structural — only `Tag::Link` and `Tag::Image` events are matched; `Event::Code` and `Event::Text` inside `Tag::CodeBlock` never produce these events; no I/O. |
