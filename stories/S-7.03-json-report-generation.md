# S-7.03: JSON Report Generation — `reporter::format_json` + schema stability contract

> **One-per-file:** This story is `S-7.03` in EPIC-07 — Output, Reporting, and Exit Codes (`E-7`).
> Adds `reporter::format_json(findings, io_errors)` to the already-scaffolded `reporter.rs`
> from S-7.02. The function emits `{"schema_version":1,"results":[...],"errors":[...]}` to
> stdout (compact, no pretty-print). Reuses the `sort_findings()` helper from S-7.02
> (ADR-005 same sort key). The `errors` array carries `target-unreadable` I/O entries that
> must NOT appear in `results`. No ANSI codes ever in JSON output.
> VP-011 proptest (same property, applied to the JSON sort path) covers sort determinism.

## Narrative

- **As a** tool author or CI system consuming `mdlinkcheck` output programmatically
- **I want to** receive a machine-parseable JSON object on stdout with a stable schema version
- **So that** I can write exhaustive switch statements over the closed reason-code taxonomy,
  reliably detect broken links in scripts without parsing human-readable text, and check
  `schema_version` to future-proof my parser against field changes

## Acceptance Criteria

> **Verification Properties:** VP-011 (`vp-011-sort-deterministic.md`, proptest, P1, DI-001)
> covers sort determinism for JSON output per VP-INDEX v1.7 — the same sort property that
> applies to text output also applies to the `results` array in JSON.
>
> BC-2.13.001: VP-011 covers the sort property. JSON parseability, ANSI-absence, and
> `results` field order are verified by acceptance corpus integration tests — there is no
> current VP for these clauses. VP-INDEX v1.7 explicitly records that VP-021 does NOT
> detect ANSI escape sequences in JSON output and does NOT verify field order (VP-021 uses
> `serde_json::Value` which ignores field order). VP-021 was removed from BC-2.13.001 rows
> in BI-052 remediation pass P7-S13-001.
>
> BC-2.13.002: test-sufficient per VP-INDEX v1.7; covered by acceptance corpus.

### AC-001 (traces to BC-2.13.001 postcondition 1)
`reporter::format_json(findings, io_errors)` returns a string containing exactly one JSON
object: `{"schema_version":1,"results":[...],"errors":[...]}`. Both `results` and `errors`
arrays are always present even when empty.
- **Test:** `test_BC_2_13_001_json_top_level_structure()`

### AC-002 (traces to BC-2.13.001 postcondition 2)
Each object in `results` has exactly these fields in this order:
`file`, `line`, `column`, `link_target`, `verdict`, `reason`.
Field order is checked via raw JSON string comparison, not via `serde_json::Value`
(which ignores order). Verified by acceptance corpus integration tests.
- **Test:** `test_BC_2_13_001_results_field_order()`

### AC-003 (traces to BC-2.13.001 postcondition 3)
The `verdict` field in each `results` entry is the string `"broken"` or `"indeterminate"`.
`"clean"` never appears in `results`; `"alive"` is an internal URL-liveness outcome (ADR-007)
and never appears in `results`.
- **Test:** `test_BC_2_13_001_verdict_values_are_broken_or_indeterminate()`

### AC-004 (traces to BC-2.13.001 postcondition 4 and invariant 1 of DI-001)
`results` is sorted by `(NFC-normalized file path ascending, line ascending, column ascending,
link_target ascending)` — the same sort key used by `format_text()` (ADR-005). Two calls with
the same input in any order produce byte-identical JSON. VP-011 proptest covers this.
- **Test:** `test_BC_2_13_001_results_sorted_deterministically()` (also exercised by VP-011)

### AC-005 (traces to BC-2.13.001 postcondition 5)
The JSON output is compact (not pretty-printed). No unnecessary whitespace between tokens.
`mdlinkcheck --format json | jq .` must succeed (machine-parseable, BC-2.13.001 invariant 5).
- **Test:** `test_BC_2_13_001_json_is_compact()`

### AC-006 (traces to BC-2.13.001 postcondition 6)
No ANSI color codes appear in the JSON output regardless of `ColorMode` or TTY status.
`format_json()` never applies ANSI sequences. Verified by acceptance corpus integration tests.
- **Test:** `test_BC_2_13_001_no_ansi_in_json_output()`

### AC-007 (traces to BC-2.13.001 postcondition 7 and invariant 6)
File-level I/O errors (reason `target-unreadable`) are placed in the `errors` array,
NOT in `results`. Each `errors` entry has exactly three fields: `file`, `reason`,
`message`. A `results` entry with `"reason":"target-unreadable"` is a bug.
- **Test:** `test_BC_2_13_001_target_unreadable_goes_in_errors_not_results()`

### AC-008 (traces to BC-2.13.001 invariant 3)
An empty scan (no findings, no I/O errors) produces
`{"schema_version":1,"results":[],"errors":[]}` exactly.
- **Test:** `test_BC_2_13_001_empty_scan_produces_empty_arrays()`

### AC-009 (traces to BC-2.13.001 invariant 4)
stdout contains only the JSON object. No diagnostic messages, no summary line appears on stdout.
The stderr summary from `format_summary()` is unaffected; it still goes to stderr (BC-2.12.003).
- **Test:** `test_BC_2_13_001_stdout_is_pure_json()` (integration test)

### AC-010 (traces to BC-2.13.002 postcondition 1 and invariant 1)
`schema_version` is always present as the first field in the top-level JSON object, and its
value is the integer `1` for the current implementation.
- **Test:** `test_BC_2_13_002_schema_version_is_first_field_and_integer_1()`

### AC-011 (traces to BC-2.13.002 postcondition 3 and invariant 3)
The `verdict` field in `results` objects contains only `"broken"` or `"indeterminate"`;
no other value is ever serialized. Reason codes in the `reason` field are from the closed
13-code taxonomy defined in `prd-supplements/error-taxonomy.md`.
- **Test:** `test_BC_2_13_002_verdict_and_reason_closed_taxonomy()`

### AC-012 (traces to BC-2.13.002 postcondition 4)
Human-readable `message` strings in the `errors` array are NOT stable across versions
and must not be used for automation. Only `reason` codes are stable. This is enforced by
documentation; no runtime test can assert instability, but the test verifies that `reason`
is a known code while `message` is a free-form string.
- **Test:** `test_BC_2_13_002_message_is_free_form_reason_is_stable()`

`format_json()` depends only on `types` (for `Finding`, `IoError`) and `serde_json`.
