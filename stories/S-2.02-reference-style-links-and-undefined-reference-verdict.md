# S-2.02: Reference-Style Links, Undefined Reference Verdict, and Parser Non-Link Exclusions

> **One-per-file:** This story is `S-2.02` in EPIC-02 — Link Extraction and Code Context Exclusion (`E-2`).
> Extends the `link_extractor` module established in S-2.01 to handle full, collapsed, and shortcut
> reference-style links with case-insensitive label matching and forward-reference resolution.
> Adds the `broken(undefined-reference-definition)` verdict for missing labels (requires
> `Parser::new_with_broken_links()` in scanner). Confirms pulldown-cmark correctly excludes
> footnote constructs and escaped brackets from link extraction.

> **VP-INDEX / BC-file discrepancy note (flag per constraint 5):** VP-INDEX v1.7 lists
> BC-2.03.002 as mapping to VP-019. BC-2.03.002 v1.6 (the BC file itself) explicitly corrects
> this: "Both VP-019 rows corrected to VP-NONE with integration test required in story — VP-019
> proves extraction deduplication (unique (dest,line,col) tuples per file call), not
> reference-definition ordering or case-insensitive label matching." This is a spec-level
> inconsistency. Per constraint 5, frontmatter follows VP-INDEX v1.7, so `verification_properties:
> [VP-019]` is present. However, the implementing test-writer MUST add dedicated integration tests
> for (a) forward-reference resolution (definitions at EOF for uses at line 1) and (b)
> case-insensitive label matching — these are NOT covered by VP-019's deduplication property.
> This gap is reported here and must NOT be silently omitted from the test suite.

## Narrative

- **As a** developer running `mdlinkcheck` on a Markdown repository that uses reference-style links
- **I want** full, collapsed, and shortcut reference forms resolved with case-insensitive label
  matching and forward references supported
- **So that** every reference link either resolves to a valid target (clean verdict) or surfaces a
  specific `undefined-reference-definition` verdict that pinpoints the use-site line where the
  undefined label appears

## Acceptance Criteria

> **Verification Properties:** VP-019 (`link_extractor` one-verdict proptest — DI-005) is in
> frontmatter per VP-INDEX v1.7 for BC-2.03.002. See VP-INDEX / BC-file discrepancy note above:
> integration tests for forward-reference resolution and case-insensitive label matching are
> ADDITIONALLY required and not covered by VP-019. BC-2.03.003 and BC-2.03.006 are test-sufficient
> per VP-INDEX v1.7 (no formal VP; covered by acceptance corpus).

### AC-001 (traces to BC-2.03.002 postcondition 1)
For a full reference link `[text][label]`, `link_extractor::extract` performs a definition-table
lookup by `label` and returns an `ExtractedLink` with `destination` set to the resolved URL from
`[label]: url`. If `docs/a.md` exists and `[ref]: docs/a.md` is defined anywhere in the file,
`[x][ref]` yields `ExtractedLink { destination: "docs/a.md", link_kind: LinkKind::RelativeFile, … }`.
- **Test:** `test_BC_2_03_002_full_reference_link_resolves_to_definition_url()`

### AC-002 (traces to BC-2.03.002 postcondition 2)
For a collapsed reference link `[text][]`, the label is derived from `text`. `[see also][]` with
`[see also]: docs/b.md` resolves to `destination: "docs/b.md"`.
- **Test:** `test_BC_2_03_002_collapsed_reference_uses_text_as_label()`

### AC-003 (traces to BC-2.03.002 postcondition 3)
For a shortcut reference link `[text]`, the label is also derived from `text`. `[FAQ]` with
`[FAQ]: faq.md` resolves to `destination: "faq.md"`.
- **Test:** `test_BC_2_03_002_shortcut_reference_uses_text_as_label()`

### AC-004 (traces to BC-2.03.002 postcondition 4)
Label matching is case-insensitive with internal whitespace normalized. `[x][REF]` successfully
resolves against `[ref]: a.md` (lowercase label definition). `[My  Link]` (double-space) resolves
against `[my link]: b.md` (whitespace collapsed). This is an integration test — not covered by
VP-019 (see VP-INDEX / BC-file discrepancy note).
- **Test:** `test_BC_2_03_002_label_matching_is_case_insensitive_and_whitespace_normalized()`

### AC-005 (traces to BC-2.03.002 postcondition 5)
When multiple definitions exist for the same label, the first definition wins. Given
`[ref]: first.md` on line 3 and `[ref]: second.md` on line 10, `[x][ref]` resolves to
`destination: "first.md"`.
- **Test:** `test_BC_2_03_002_first_definition_wins_on_duplicate_labels()`

### AC-006 (traces to BC-2.03.002 postcondition 6)
`![alt][imgref]` image references are extracted and classified identically to link references.
`[imgref]: logo.png` → `ExtractedLink { destination: "logo.png", link_kind: LinkKind::RelativeFile, … }`.
- **Test:** `test_BC_2_03_002_image_reference_extracted_same_as_link_reference()`

### AC-007 (traces to BC-2.03.002 postcondition 7 and invariant 4)
The reported `Finding` position for any reference form is the **use-site** byte offset — the
position of the `[text]` span in the source, never the position of the `[label]: url` definition
line. For EC-202: two uses of `[x][ref]` at line 3 and line 7 with `[ref]: missing.md` at EOF
produce two separate findings with `line=3` and `line=7` respectively. Reporting at the
definition line is FORBIDDEN (BC-2.03.002 invariant 4).
- **Test:** `test_BC_2_03_002_finding_position_is_use_site_not_definition_site()`
- **Test:** `test_BC_2_03_002_ec202_two_uses_same_label_produce_distinct_line_numbers()`

### AC-008 (traces to BC-2.03.002 invariant 1)
A reference definition that appears AFTER its use is still resolved. `[x][ref]` on line 1 with
`[ref]: docs/a.md` at EOF yields a resolved link, not an undefined-reference verdict.
This is an integration test — pulldown-cmark resolves forward references by construction, but
it MUST be explicitly verified (see VP-INDEX / BC-file discrepancy note).
- **Test:** `test_BC_2_03_002_forward_reference_definition_at_eof_resolves_for_line_1_use()`

### AC-009 (traces to BC-2.03.002 invariant 3)
Unused reference definitions (`[ref]: docs/a.md` that is never referenced in the file) produce
no `ExtractedLink` entry and no finding. The definition is silently ignored.
- **Test:** `test_BC_2_03_002_unused_reference_definition_produces_no_finding()`

### AC-010 (traces to BC-2.03.003 precondition 3 and postcondition 1)
The pulldown-cmark `Parser` in `scanner.rs` MUST be constructed via
`Parser::new_with_broken_links(src, &options, Some(broken_link_callback))` where
`broken_link_callback` returns `None`. Without this callback, undefined reference links are
emitted as plain text and no `Tag::Link` event is produced — the verdict is unreachable. The
integration test confirms that `[see also][missing-label]` (where no `[missing-label]:` definition
exists) produces verdict `broken` with reason `undefined-reference-definition`, exit code 1.
- **Test:** `test_BC_2_03_003_undefined_reference_yields_broken_verdict()`

### AC-011 (traces to BC-2.03.003 postcondition 2)
The reason code for an undefined reference label is exactly `undefined-reference-definition`
(not `file-not-found`, not `anchor-not-found`). This is a distinct failure class — the target
URL was never resolved because no definition exists.
- **Test:** `test_BC_2_03_003_reason_code_is_undefined_reference_definition()`

### AC-012 (traces to BC-2.03.003 postcondition 3)
The `link_target` field in the `Finding` for an undefined reference label is the label text
itself (e.g., `"missing-label"`), not a path or URL.
- **Test:** `test_BC_2_03_003_link_target_field_is_label_text()`

### AC-013 (traces to BC-2.03.003 postcondition 4)
No filesystem lookup or URL fetch is attempted for an undefined reference label. The
`broken(undefined-reference-definition)` verdict is set during extraction, before any
path or URL resolution phase.
- **Test:** `test_BC_2_03_003_no_filesystem_lookup_for_undefined_reference()`

### AC-014 (traces to BC-2.03.006 postcondition 1)
Footnote-style constructs `[^1]` and `[^note]` produce zero `ExtractedLink` entries.
A file containing `See [^1] for details.\n\n[^1]: Source text.` exits 0 with no findings.
- **Test:** `test_BC_2_03_006_footnote_reference_produces_no_extracted_link()`

### AC-015 (traces to BC-2.03.006 postcondition 2)
`[^1]: Some footnote text` is not treated as a reference definition for link resolution.
`[x][^1]` does NOT resolve against `[^1]: text`; it is either a malformed label or
an undefined reference — but never a resolved link via the footnote definition.
- **Test:** `test_BC_2_03_006_footnote_definition_not_used_for_link_resolution()`

### AC-016 (traces to BC-2.03.006 postcondition 3)
Escaped brackets `\[not a link\](url)` produce zero `ExtractedLink` entries. pulldown-cmark
handles escape sequences by construction — the content is emitted as text nodes, not as
`Tag::Link` events. A file containing only `\[not a link\](missing.md)` exits 0 with no findings.
- **Test:** `test_BC_2_03_006_escaped_brackets_produce_no_extracted_link()`

the `*Unknown` `LinkType` variants that surface undefined references are never emitted.

**Subsystem anchor:** SS-03 owns this story's scope because all three BCs are in the Link
Extraction subsystem, with `link_extractor` as primary module per ARCH-INDEX Subsystem Registry.
Scanner is a secondary module only for BC-2.03.003 parser configuration.

**Dependency anchor:** S-2.02 depends on S-2.01 because reference-style link resolution
extends the same `link_extractor::extract` function established in S-2.01. The `ExtractedLink`
and `LinkKind` types from S-2.01 are prerequisites for the reference-form expansion in this story.

## Purity Classification

| Module | Classification | Justification |
|--------|---------------|---------------|
| `link_extractor` | pure-core | Reference-style link resolution is handled by pulldown-cmark's parser (which does the full-document scan and definition table lookup) before `extract` is called. The events passed to `extract` already encode whether a reference is resolved or `*Unknown`. `extract` performs no I/O. |
| `scanner` (parser configuration) | effectful-shell | Scanner constructs the pulldown-cmark parser and must pass `Parser::new_with_broken_links()` with a `broken_link_callback`. This is the only effectful touchpoint in this story — the callback configuration, not link resolution logic. |

## Architecture Compliance Rules (MANDATORY)

| Rule | Source | Enforcement |
|------|--------|-------------|
| `scanner.rs` MUST construct the pulldown-cmark parser with `Parser::new_with_broken_links()` and a `broken_link_callback` that returns `None`. A plain `Parser::new()` silently discards undefined references as text nodes, making the `undefined-reference-definition` verdict unreachable | BC-2.03.003 precondition 3 and invariant 2; ADR-003 §Undefined reference detection | Code review: search `scanner.rs` for `Parser::new_with_broken_links`; absence is a hard defect |
| Reference-style link label matching MUST follow CommonMark ASCII case folding (not locale-dependent). This is handled by pulldown-cmark by construction — do not implement custom case folding | BC-2.03.002 invariant 2; ADR-003 (CommonMark+GFM parse mode) | Code review: confirm no custom `to_lowercase()` or locale-aware comparison in `link_extractor` |
| Finding positions MUST be use-site byte offsets. Attribution to the `[label]: url` definition line is FORBIDDEN per BC-2.03.002 invariant 4. Violating this collapses two broken-link findings into one (silent data loss) | BC-2.03.002 postcondition 7 and invariant 4 | Dedicated test: EC-202 (two uses at distinct lines must produce two findings with distinct line numbers) |
| `link_extractor` and `url_classifier` MUST NOT contain any I/O calls | ADR-001 (pure-core boundary); purity-boundary-map.md §Boundary Rule | `cargo deny` + code review |
| `pulldown-cmark` version MUST be exactly `0.13.4` | ADR-003; dependency-graph.md §mdlinkcheck-core | `Cargo.lock` inspection |
