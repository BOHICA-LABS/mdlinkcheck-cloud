# S-4.01: Pass 1.5 DirIndex Data Product

> **One-per-file:** This story is `S-4.01` in EPIC-04 — Relative File Link Resolution (`E-4`).
> Delivers the `DirIndex` type definitions and the Pass 1.5 effectful construction logic in
> `app.rs` that populates `DirIndex` from every extracted link destination. This data product
> enables `path_resolver` (SS-07) to be a genuinely pure function — all filesystem reality
> is captured in `DirIndex` before Pass 2 begins.

## Narrative

- **As a** developer integrating `mdlinkcheck` into CI
- **I want to** have `DirIndex` populated before any link-resolution pass begins
- **So that** `path_resolver` can perform NFC case-sensitive directory-entry lookup without
  ever calling `fs::read_dir`, `fs::metadata`, or `Path::exists` — keeping the pure-core
  module formally Kani-verifiable and producing reproducible verdicts regardless of
  macOS APFS case-folding

## Acceptance Criteria

> **Verification Properties:** All BCs in this story are test-sufficient per VP-INDEX v1.7
> for the DirIndex construction scope (effectful shell; Kani not applicable). Coverage is by
> acceptance corpus integration tests and the unit tests below.

### AC-001 (traces to BC-2.07.002 postcondition 5)
After Pass 1.5 completes, `DirIndex` contains an entry for every unique parent directory of
every extracted link destination across all link types: `.md` files already in the scan set,
`.md` files outside the scan set (gitignored, above root), non-`.md` files, and directory
references. No link destination's parent directory is missing from `DirIndex`.
- **Test:** `test_BC_2_07_002_dirindex_populated_all_link_types()`

### AC-002 (traces to BC-2.07.002 postcondition 5)
A link destination that references a directory outside the scan set (e.g., a path that would
resolve into a `.gitignore`-excluded directory) has its parent directory present in `DirIndex`.
Pass 1.5 is not restricted to scan-root directories — it follows each link destination's
parent directory regardless of whether that directory is in the scan set.
- **Test:** `test_BC_2_07_002_dirindex_covers_out_of_scan_dirs()`

### AC-003 (traces to BC-2.07.002 invariant 1)
All root-relative link resolutions within a single `mdlinkcheck` run use the same git repo
root value. The git repo root is determined once at startup (via `git rev-parse --show-toplevel`
or CWD fallback) and cached; it is not re-computed per file or per link.
- **Test:** `test_BC_2_07_002_git_root_determined_once_per_run()`

### AC-004 (traces to BC-2.07.002 invariant 3)
When no git repository is found (the scan target is not inside a git repo and `git` is not in
`PATH`), `app` falls back silently to the deepest common ancestor of all PATH arguments (or CWD
for default scan). No error is emitted; the fallback is deterministic.
- **Test:** `test_BC_2_07_002_fallback_to_scan_root_in_non_git_dir()`

### AC-005 (traces to BC-2.07.001 invariant 3)
`DirIndex` is the sole mechanism by which `path_resolver` performs existence and entry-kind
checks. After Pass 1.5 builds `DirIndex` by calling `fs::read_dir` on each unique parent
directory, `path_resolver::resolve` is never called with a destination whose parent directory
is absent from `DirIndex`. No `fs::read_dir`, `fs::metadata`, or `Path::exists` calls are
made inside `path_resolver` — it receives `DirIndex` as input data only.
- **Test:** `test_BC_2_07_001_path_resolver_requires_no_direct_fs_calls()` (property-based: call
  `path_resolver::resolve` with a synthetic `DirIndex`; verify the function is pure — no
  external state access required)

### AC-006 (traces to BC-2.07.003 precondition 2)
For every link destination processed in Pass 2, the parent directory of the resolved path is
present in `DirIndex`. Pass 1.5a guarantees this for every extracted link destination — all
link types (.md files, non-.md files, directories) — before Pass 2 begins, making BC-2.07.003
precondition 2 ("parent directory is present in DirIndex") always satisfied.
- **Test:** `test_BC_2_07_003_dirindex_precondition_2_always_satisfied()`

### AC-007 (traces to BC-2.07.002 postcondition 3)
`DirIndex` construction visits each unique parent directory at most once. If multiple links
reference files in the same directory, `fs::read_dir` is called once for that directory and the
entries are cached. This prevents redundant I/O and ensures deterministic behavior.
- **Test:** `test_BC_2_07_002_dirindex_visits_each_dir_at_most_once()`

## Architecture Mapping

| Component | Module | Pure/Effectful |
|-----------|--------|---------------|
| DirIndex type | `crates/mdlinkcheck-core/src/types.rs` | pure-core (type definition only) |
| DirEntryInfo, EntryKind types | `crates/mdlinkcheck-core/src/types.rs` | pure-core (type definition only) |
| Pass 1.5 construction | `crates/mdlinkcheck/src/app.rs` | effectful-shell (`fs::read_dir`) |
| Git root detection | `crates/mdlinkcheck/src/app.rs` | effectful-shell (subprocess `git rev-parse`) |

## Edge Cases

| ID | Scenario | Expected Behavior |
|----|----------|-------------------|
| EC-026 | Root-relative link `/docs/api.md` in a git repo | `app` determines git root via `git rev-parse --show-toplevel`; parent directory `/docs/` added to DirIndex |
| EC-027 | Root-relative link `/docs/api.md` in a non-git directory | `app` falls back to scan root (deepest common ancestor of PATH args / CWD); parent directory added to DirIndex using fallback root |
| EC-028 | Multiple links pointing to files in the same directory | `fs::read_dir` called once for the shared parent directory; entries cached in `DirIndex` |
| EC-029 | Link destination is itself a directory (`docs/`) | Parent of `docs/` is added to `DirIndex`; `docs/` itself is also added (its entries needed to determine it is a Dir) |
| EC-030 | Link destination references a file above repo root (`../../escape.md`) | After logical resolution, parent directory is still collected and added to `DirIndex`; path_resolver applies existence check and produces `file-not-found` if path escapes |

## Purity Classification

| Module | Classification | Justification |
|--------|---------------|---------------|
| `types.rs` (DirIndex types) | pure-core | Type definitions only; no functions, no I/O |
| `app.rs` (Pass 1.5 construction) | effectful-shell | Calls `fs::read_dir`; this is the ONLY place in the pipeline where directory I/O for link resolution is performed |
| `path_resolver.rs` (consumer) | pure-core | Receives `DirIndex` as data; performs no I/O; DirIndex is the purity seam |

## Forbidden Dependencies

`crates/mdlinkcheck-core` MUST NOT gain a dependency on `std::fs` for path resolution.
If `path_resolver.rs` gains any `fs::read_dir`, `fs::metadata`, or `Path::exists` call, the
build MUST fail (CI check: `grep -rn 'fs::read_dir\|fs::metadata\|Path::exists' crates/mdlinkcheck-core/src/path_resolver.rs`
must return empty). The purity guarantee (ADR-001, SR-016) is non-negotiable — it enables
formal verification of path resolution correctness.
