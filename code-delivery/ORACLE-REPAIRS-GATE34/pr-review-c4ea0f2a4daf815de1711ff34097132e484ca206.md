## BLOCKING

### BLOCKING-1 — `check-ec-injectivity`: BC-vs-registry comparison reads the wrong `test-vectors.md` column, so most SCENARIO-MISMATCH findings are artifacts

**File:** `scripts/spec-lint/check-ec-injectivity.py` — `extract_tv_rows()` (unchanged) consumed by the new `_compare_bc_to_registry()` path in `main()`

`extract_tv_rows()` assumes a single TV schema and hard-codes column 3 as the description:

```python
m = re.match(
    r"^\|\s*(TV-[\w]+)\s*\|\s*(EC-\d{1,4}[a-z]?)\s*\|\s*(.+?)\s*\|.*?\|\s*(\d|n/a)\s*\|\s*(.+?)\s*\|",
    line,
)
desc = m.group(3).strip()   # ← assumed to be "Description"
```

`test-vectors.md` has 15 table sections with at least **seven distinct schemas**. Column 3 is not a description in six of them:

```
line  69: | TV | EC | Fixture Description | Flags | Expected Exit | Expected Verdict | Reason |
line  98: | TV | EC | Source MD File      | Link | Filesystem | Expected Exit | Expected Verdict | Reason |
line 126: | TV | EC | Source MD           | Heading | Link | Expected Exit | Verdict | Notes |
line 175: | TV | EC | Link                | Mock Server / Setup | Flags | Expected Exit | Verdict |
line 199: | TV | EC | Source MD Content   | Expected Exit | Expected Verdict | Notes |
line 234: | TV | EC | Input               | Flags | Expected Exit | Expected Output |
line 359: | TV | EC | Description         | Flags | Exit | Verdict | Notes |
```

Meanwhile `extract_ec_rows()` takes the BC's first non-separator cell after the EC ID — a prose **Description**. So for every EC whose TV row lives in a `Source MD File` / `Link` / `Input` / `Source MD Content` section, the checker computes Jaccard between a prose description and a bare filename or URL. Disjoint by construction → J = 0.00 → DIVERGENT → `return 1`.

**Failure scenario (live corpus, reproduced):**

```
SCENARIO-MISMATCH EC-085: behavioral-contracts/ss-10/BC-2.10.001.md:68
  BC  : 'HEAD succeeds (200)'
  TV  : '`https://example.com/redirects`'        ← this is the "Link" column, not a description
  (J=0.00)

SCENARIO-MISMATCH EC-023: behavioral-contracts/ss-07/BC-2.07.001.md:59
  BC  : '`[x](./same-dir.md)`'
  TV  : '`docs/a.md`'                            ← "Source MD File" column
  (J=0.00)
```

**13 of the 17 SCENARIO-MISMATCH findings** have a filename or URL on the TV side (EC-023, EC-024, EC-078, EC-085, EC-086, EC-088, EC-092 ×2, EC-124, EC-126, EC-127, EC-130, EC-131). Only 4 (EC-134, EC-135, EC-142, EC-146) compare prose to prose, i.e. only 4 are candidates for being real. The calibration case cited in the docstring (EC-142) is one of the 4 that happens to land in a `Description`-schema section — which is why the mechanism looked sound during development.

The same defect pollutes the 43 REQUIRES-ADJUDICATION entries.

**Why this blocks:** the checker exits 1 on these, and the PR's headline deliverable is the baseline that the content workstream will work from. Handing over 17 "hard findings" of which ~13 are column-alignment artifacts sends that workstream to remediate a frozen corpus for non-defects.

**Suggested fix (checker-side only):** make `extract_tv_rows()` schema-aware — track the most recent header row, locate the `Description` column by name, and skip sections that have no description column rather than substituting column 3. Sections whose column 3 is `Fixture Description` / `Description` are comparable; the rest should be excluded from the BC-vs-registry comparison (and that exclusion needs to be visible in the coverage line, e.g. `N of M citations comparable`).

### BLOCKING-2 — `check-adr-consistency`: POLICY 19 Patterns 2 and 3 skip the `_is_spec_ref_id()` discriminator, so decision IDs are reported as phantom reason codes

**File:** `scripts/spec-lint/check-adr-consistency.py` — `check_broad_corpus()`

The file defines exactly the right discriminator and documents its purpose:

```python
_SPEC_REF_ID_RE = re.compile(r'^[A-Z]{1,5}-\d')
def _is_spec_ref_id(code: str) -> bool: ...
```

It is applied in Pattern 1 only. Patterns 2 (`VERDICT_PAREN_CODE_RE`) and 3 (`TAXONOMY_CODE_RE`) never call it. Pattern 2 additionally omits Pattern 1's `if "-" not in code: continue` guard.

**Failure scenario (live corpus, reproduced):**

```
behavioral-contracts/ss-10/BC-2.10.003.md:53: verdict reason code 'DI-010' not in closed taxonomy (POLICY 19)
  2. `http-timeout` is indeterminate, not broken (DI-010).

verification-properties/vp-007-http-verdict-total.md:160: verdict reason code 'D-018' not in closed taxonomy (POLICY 19)
  "400 after GET fallback must not produce broken (D-018)");

verification-properties/vp-007-http-verdict-total.md:162: verdict reason code 'D-018' ...  (same shape)

prd.md:679: verdict reason code 'clean' not in closed taxonomy (POLICY 19)
```

Confirmed directly:

```
_is_spec_ref_id: DI-010=True   D-018=True   clean=False
VERDICT_PAREN_CODE_RE on the DI-010 line -> ['DI-010']
VERDICT_PAREN_CODE_RE on prd.md:679      -> ['clean']
```

`DI-010` and `D-018` are decision cross-references appended as citations — the exact class `_is_spec_ref_id()` exists to exclude. `clean` is a **verdict**, and the file's own POLICY 12 section states that verdicts are `clean/broken/indeterminate`; reporting `clean` as an out-of-taxonomy reason code is self-contradictory.

**5 of the 26 findings** come from this defect.

**Suggested fix:** hoist the Pattern 1 filters (`"-" in code`, `not _is_spec_ref_id(code)`, the `--` CLI-flag skip) into one shared `_is_reason_code_candidate(code)` helper and call it from all three patterns. That also removes the current duplication of the inline exemption set (see ADVISORY-7).

### BLOCKING-3 — `check-adr-consistency`: POLICY 19 Pattern 1's context guard is not a reason-code discriminator, so arbitrary hyphenated identifiers are reported as phantom reason codes

**File:** `scripts/spec-lint/check-adr-consistency.py` — `check_broad_corpus()`, Pattern 1

The candidate test is "any backtick-quoted token containing a hyphen, on a line containing one of `reason`, `verdict`, `broken`, `exit`, `error`, `taxonomy`, `indeterminate`". In a spec corpus about broken links, that context guard admits essentially every line, and the token test admits every kebab-case identifier.

**Failure scenarios (live corpus, reproduced):**

| Reported "reason code" | Actual line content | What it really is |
|---|---|---|
| `macos-latest` | `nfr-catalog.md:94` — "D-043 narrows the platform matrix to macOS (`macos-latest`) only…" | CI runner label |
| `Retry-After` ×2 | `BC-2.10.004.md:85` — "Host returns 429 with HTTP-date `Retry-After` (future)" | HTTP response header |
| `foo-1`, `Foo-1`, `foo-1-1`, `foo-2` (5 occurrences) | `test-vectors.md:134`, `168`, `169`, `prd.md:761` — "`[b](#foo-1)`, `[c](#foo-1-1)` … `Foo-1` normalizes to `foo-1`" | anchor-slug collision test fixtures |
| `test-sufficient` ×3 | `prd.md:743`, `744`, `746` — "`test-sufficient` replaced with **VP-023**…" | the POL-14 VP sentinel introduced by merged PRs #9 and #10 |

The `test-sufficient` case is the sharpest: `check-placeholders.py` deliberately accepts `test-sufficient` as a valid VP sentinel (D-078 / POL-14, merged in `d4e76fa` and `f8ee4eb`), while the new POLICY 19 code calls the same token a phantom reason code. Two checkers in the same suite now disagree about the same identifier.

Counting only the unambiguous cases (`D-018` ×2, `DI-010` ×2, `clean`, `Retry-After` ×2, `macos-latest`, `foo-*` ×5, `test-sufficient` ×3), **at least 16 of the 26 findings are not reason codes at all**. **Why this blocks:** same reason as BLOCKING-1. No edit to `.factory/specs/` could resolve these — `Retry-After` and `macos-latest` are correct content. The signal-to-noise ratio (≈3 real of 26) means the published baseline cannot be used as a work queue, and the number is quoted as a headline deliverable in the PR body and in the traceability table (`26 violations now detected | CLOSED`).

**Suggested fix:** replace the keyword-in-line context guard with a positional one — require the backticked token to be in a syntactic reason-code position (a `Reason` table column, or immediately following `reason code`/`reason:`/`sub_reason`), the way Pattern 3 already binds to `(consistent with X taxonomy)`. A whole-line keyword OR is not a position-based predicate in the D-081 sense the docstrings claim.

## ADVISORY

### ADVISORY-1 — Three of the four "corpus-completeness assertions" are tautological, and the comments claim otherwise

`check-holdout-boundary.py` states:

```python
# CORRECTION 2 (D-057 / POLICY 11): compute total spec corpus independently so
# the completeness assertion is falsifiable — if the loop filter drifts from this
# ground-truth count, the check fails loudly rather than silently under-counting.
total_corpus = sum(1 for f in SPECS.rglob("*.md") if should_check_file(f))
```

The scan loop is `for md_file in sorted(SPECS.rglob("*.md")): if not should_check_file(md_file): continue`. Same iterable, same predicate — `files_checked != total_corpus` is unreachable, and the `return 2` branch is dead code. The total is not computed independently; it is computed identically.

Same shape in:
- `check-placeholders.py`: `total_files = sum(1 for _ in SPECS.rglob("*.md"))` vs an unfiltered loop over the same rglob. `completeness` can never be `INCOMPLETE`.
- `check-ec-injectivity.py`: `files_scanned` increments unconditionally over the same rglob as `total_files`. The `return 1` gap branch is dead code.

Only `check-adr-consistency.py` has a genuinely falsifiable assertion, because it sums two differently-filtered partitions against a third predicate. It is worth noting that this is the one the PR presents as the model — the other three imitate its output string without imitating its structure.

**Suggested fix:** derive the total from a source the loop does not use (e.g. `git ls-files '.factory/specs/**/*.md'`, or the file count recorded by another checker), or drop the "falsifiable" claim from the comments.

### ADVISORY-2 — The suppression guard's Pass 2 "proof" is a grep for a print-string, so the class is not closed

`COMPLETENESS_PATTERN='of[[:space:]]+[0-9a-zA-Z_{}]+[[:space:]]+spec files'` is matched against raw file text. A checker satisfies Pass 2 by containing that substring anywhere — including in a comment (already noted as SEC-003), in a docstring, or in a hardcoded string with no runtime meaning. Combined with ADVISORY-1, three of the four checkers currently "prove" their scope with an assertion that cannot fail.

Pass 1 is also narrower than claimed. `PATH_SHAPE_PATTERN='\{[[:space:]]*str\((REPO|SPECS)[[:space:]]*/[[:space:]]*"'` matches only a set literal opening with `str(REPO / "` or `str(SPECS / "`. All of these evade both passes:

```python
EXCL = set(); EXCL.add(str(SPECS / "prd.md"))     # not a set literal
EXCL = {f"{SPECS}/prd.md"}                         # f-string, no str(
EXCL = {str(SPECS.joinpath("prd.md"))}             # no " / " operator
SKIPPED_FILES = ("prd.md",)                        # name not in vocabulary, no path shape
```

The `spec_lint_primitives.py` docstring asserts the guard "catches `EXCLUDE_PATHS` regardless of variable name" — true only for that one literal shape. The PR body's own note that it "Corrected false 'closes the class structurally' claim in comments" is the right instinct; the remaining claim is still stronger than the implementation.

**Suggested fix:** state the guard's honest contract (it detects two enumerated shapes, and the completeness assertion is a convention not a proof), or make Pass 2 verify the assertion at runtime — e.g. have the harness parse each checker's coverage line and cross-check the file count against an externally computed corpus size.

### ADVISORY-3 — `check-holdout-boundary`: the prose predicate false-positives on mermaid edges and ordinary prose

`->` matches inside mermaid's `-->`, and `broken`/`clean`/`alive`/`indeterminate` are ordinary words in this domain. Reproduced with a two-file hermetic corpus:

```
diagram.md:5: holdout EC-079 has concrete prose scenario in visible artifact (BI-049)
  A["EC-079 retired"] --> B["broken links path"]

diagram.md:8: holdout EC-151 has concrete prose scenario in visible artifact (BI-049)
  - Coverage note: EC-151 is reserved -- see holdout policy -> the pool is clean.
```

Neither line contains a scenario. This is latent rather than active — the live corpus yields exactly the one true EC-151 finding — but any future architecture diagram that names a holdout EC ID will trip it.

**Suggested fix:** require `->` not to be part of `-->` (or drop the ASCII arrow and require `→`), and require the verdict word to be adjacent to the arrow rather than anywhere in the suffix.

### ADVISORY-4 — The documented residual BI-049 bypass has no selftest

`is_concrete_scenario_prose()` documents its own hole:

```
Known limitation: a real breach written as "→ broken occurs for EC-151 (input X)"
— where the arrow appears BEFORE the EC ID — would not be detected.
```

That shape is the exact mirror of selftest 7d's must-NOT-flag case, so the two constraints are in tension and there is no test pinning the boundary between them. A future attempt to close the hole has no regression net and will silently reintroduce the `prd.md:630` false positive.

**Suggested fix:** add an xfail-style or explicitly-documented negative selftest recording the known-uncaught shape, so the gap is tracked mechanically rather than only in a comment.

### ADVISORY-5 — `check-adr-consistency`'s completeness assertion aborts on benign corpus growth

`adrs_checked` comes from `ADR_DIR.glob("ADR-*.md")` (non-recursive, name-prefixed), while `_in_spec_corpus` counts everything and `should_check_for_broad_p19` excludes the whole `/architecture/decisions/` subtree. So any `.md` in `decisions/` that is not named `ADR-*.md`, and any file in a subdirectory of `decisions/`, becomes unaccounted for. Reproduced:

```
$ # decisions/README.md added, nothing else
ERROR: scope gap — 1 broad + 0 ADRs = 1 scanned, but corpus total is 2; check
_in_spec_corpus / should_check_for_broad_p19 filter alignment
exit=2
```

Adding a README to the decisions directory takes the checker from "running" to "refusing to run". The intent (fail loudly on filter drift) is right; the trigger is over-broad.

**Suggested fix:** route non-`ADR-*.md` files under `decisions/` to the broad POLICY 19 path instead of excluding the whole directory by path prefix, and use `rglob` for the ADR path.

### ADVISORY-6 — `_compare_bc_to_registry` compares against only the first registry row for an EC ID

`tv_desc = tv_occs[0][1]`. Given 15 TV table sections, an EC ID can legitimately appear in more than one, and only the first is ever consulted. A BC that agrees with the second registry row is reported as divergent. This compounds BLOCKING-1.

**Suggested fix:** compare against all TV rows for the EC and take the best (highest-Jaccard) match.

### ADVISORY-7 — A hardcoded name-keyed exemption set was introduced, inconsistently, inside the new POLICY 19 code

```python
if code not in valid_reason_codes and code.lower() not in {
    "http-indeterminate", "https-downgrade", "private-ip",
}:
```

This literal appears in Pattern 1 and Pattern 2 and is absent from Pattern 3. It is a hardcoded allowlist of code names — the same category D-039 rules out for the closed set, just keyed on names instead of paths — and because it is an inline literal rather than a named variable, both `SUPPRESSION_PATTERN` and `PATH_SHAPE_PATTERN` are blind to it. The duplication also means the two copies can drift.

**Suggested fix:** if these three are legitimate codes, add them to `error-taxonomy.md` so `extract_closed_reason_codes()` picks them up at runtime; if they are not codes, exclude them positionally. Either way there should be one definition, applied uniformly.

### ADVISORY-8 — `check-placeholders` Predicate 1's exemption region is wider than the coverage line implies

Any `### v<digits>` heading opens an exemption region that runs until the next H1/H2/H3, and H4+ deliberately does not close it. In `prd.md` that covers the whole changelog. I measured the live effect by disabling each predicate in a copy of the checker:

- Predicate 1 disabled → 4 additional findings (`prd.md:644` VP-TBD ×2, `prd.md:650` SS-TBD ×2).
- Predicate 2 disabled → 0 additional findings.

So the exemption is narrow *in practice today*, and this is a genuine improvement over wholesale path exclusion. The residual concern is that the reported guarantee — `0 live placeholders found across 134 of 134 spec files (complete)` — measures **files scanned**, not lines exempted. A live placeholder introduced anywhere inside the changelog region would be silently exempt while the checker still prints "complete". That is a weaker property than the wording suggests.

**Suggested fix:** report the exemption count alongside the coverage count, e.g. `0 live placeholders, 4 exempt (changelog-narrative), across 134 of 134 spec files`. That makes the exemption surface visible in the baseline rather than folded into a green line.

### ADVISORY-9 — Scope-gap exit codes are inconsistent and untested

`check-holdout-boundary` and `check-adr-consistency` return 2 on scope gap; `check-ec-injectivity` returns 1 for the equivalent condition. No selftest exercises any exit-2 path, and the CI wrapper's handling of exit 2 vs exit 1 is not covered by the diff.

## COSMETIC

**COSMETIC-1** — `check-placeholders.py`: `line.startswith("## ") and not line.startswith("### ")` — the second clause can never be false when the first is true (`"### x"` does not start with `"## "`). Same for the `### `/`#### ` and `# `/`## ` pairs. Harmless, but reads as if it were load-bearing.

**COSMETIC-2** — `check-placeholders.py`: a bare `#` heading line (no text) falls into the H4+ `else` branch, clearing H2 context but not H3. An H1 written as `#` therefore does not close a changelog narrative section.

The clean arm asserts the adjudication bucket (J≈0.091, `1 require adjudication`); the defect arm asserts divergence. Both are correct in the test — the row just describes them as one thing.

**COSMETIC-4** — `check-placeholders.py` docstring claims Predicate 1 covers "prd.md:509 `[filled by architect]` under ### v1.9 — EXEMPT". That occurrence is inside a backtick span and is actually suppressed by Predicate 2; Predicate 1's live coverage is `prd.md:644` and `:650` only. Verified by disabling each predicate independently.

**COSMETIC-5** — `spec_lint_primitives.py`: the new docstring re-lists the full guard vocabulary in prose. `run-selftests.sh` explicitly warns that a second copy of a guard pattern is the original B-7 defect class; a prose copy will drift from `SUPPRESSION_PATTERN` the next time a name is added. Referring to the canonical definition by name would be safer.

## Assessment

The harness work here is the strongest part of the PR and I would not want it reworked: the gated clean-pass/defect-fail pattern, the single-definition guard variables, the enforced test count, and the per-test mutation-verify notes are all doing real work, and I confirmed 82/82 locally rather than taking the badge at face value. BI-047 and BI-049 land cleanly — coverage genuinely goes to 134/134 with no path-keyed exclusions, and the EC-151 breach is genuinely caught without the `prd.md:630` false positive.

BI-050 and BI-051 are where I have to block. Both broadened their *reach* correctly and both are now finding things, but neither has a sound discriminator for what it is looking at: BI-051 compares a prose description against whatever token happens to sit in the third table column, and BI-050 treats every kebab-case identifier near the word "error" as a reason code. The result is that roughly 16 of 26 and roughly 13 of 17 published findings are artifacts of the checkers rather than properties of the corpus.

That matters specifically *because* of gate #34's oracles-first ordering. The whole point of repairing the oracles before touching content is that the resulting baseline becomes the authoritative work queue. A baseline where the majority of entries cannot be resolved by any content change — `Retry-After` is a header, `macos-latest` is a runner label, `test-sufficient` is a sentinel this repo deliberately introduced two PRs ago — inverts that: the content workstream would spend its first pass discovering that the oracle is still wrong. Better to fix the discriminators now, re-run, and hand over a baseline that is red for reasons that are all real.

None of the above asks for a single edit under `.factory/specs/` or `.factory/holdout-scenarios/`. All three blocking fixes are in `scripts/spec-lint/`.
