### BLOCKING-6 — `is_header_row` still lets a data row containing a bare `reason` cell escape Pattern 1 entirely (BLOCKING-5c masking vector remains live)

| Field | Value |
|-------|-------|
| Severity | **blocking** |
| Category | coherence / oracle-blindness |
| File | `scripts/spec-lint/check-adr-consistency.py:328` |

The 5c repair added separator-confirmed header detection so a data cell whose value is
exactly `reason` can no longer hijack `current_reason_col_p1`. But three lines further down,
Pattern 1 still gates on the *old* content heuristic:

```python
is_header_row = any(cell.lower() in ("reason", "reason code") for cell in cells)
if (not is_header_row
        and not slp.is_table_separator_row(cells)
        and current_reason_col_p1 is not None
        ...
```

Any **data** row that happens to contain a bare cell equal to `reason` or `reason code` is
still classified as a header row and skipped wholesale — so a phantom code sitting in the
real Reason column *on that row* is silently missed. The column index is protected; the row
is still dropped. This is the same silent-masking class BLOCKING-5c named, reached by a
different code path, and the fix's own comment ("prevents data cells whose value is exactly
`reason` from … masking phantoms") therefore overstates what landed.

**Failure scenario (reproduced against the covered SHA):**

```markdown
| Case   | Reason           | Notes               |
|--------|------------------|---------------------|
| reason | `phantom-zzz`    | should be flagged   |
| other  | `phantom-yyy`    | control             |
```

```
check-adr-consistency.py output:
  probe-a.md:4: reason code 'phantom-yyy' not in closed taxonomy (POLICY 19)
  → phantom-zzz on line 3 is NOT reported
```

With only the first row present the checker exits **0** and reports **`0 reason-code
occurrences validated`** — a blind pass.

**Why selftest 5j did not catch it.** 5j places the bare `reason` cell in one row and the
phantom in a *different* row, so it only exercises the hijack path. Worse, 5j's clean leg is
vacuous: its clean fixture is

```markdown
| Status | Reason           | Notes  |
|--------|------------------|--------|
| broken | `file-not-found` | reason |
```

and under the delivered code that single data row is skipped by `is_header_row`, so the
clean-pass assertion passes while validating **0 occurrences** — it proves nothing about the
Reason column being read at all. I confirmed this directly: the checker prints
`Check passed: 0 reason-code occurrences validated` on 5j's clean fixture.

**Suggested fix — delete the guard (3 lines → 1).** With separator-confirmed header
detection in place, `is_header_row` is now redundant for its original purpose: a header row
is always processed *before* its separator, and the preceding non-table line has already
reset `current_reason_col_p1` to `None`, so the `current_reason_col_p1 is not None` guard
already excludes header rows. (A stacked second header row is also safe — `reason code`
contains a space and fails Branch B's `fullmatch`.)

```python
            if (not slp.is_table_separator_row(cells)
                    and current_reason_col_p1 is not None
                    and current_reason_col_p1 < len(cells)):
```

**I verified this patch before proposing it:**

1. Probe above now reports **both** `phantom-zzz` and `phantom-yyy` — vector closed.
2. Full corpus output is **byte-identical** to the delivered PR (`4 violations`, `79
   occurrences`, `134 of 134 files`) — the published baseline table does not move.
3. Selftest-neutral (no test's clean or defect leg changes verdict).

Please also tighten selftest 5j so the phantom sits **on** the row carrying the bare
`reason` cell, and assert a non-zero `occurrences validated` count in the clean leg so the
assertion cannot be vacuous again.

### WARNING-8 — Branch A's `re.match` admits backtick-leading prose in a Reason column as a reason code (new false-positive surface)

| Field | Value |
|-------|-------|
| Severity | suggestion (warning) |
| Category | coherence / false-positive |
| File | `scripts/spec-lint/check-adr-consistency.py:352` |

Relaxing Branch A from `fullmatch` to `match` was necessary for 5b, but it now treats *any*
Reason-column cell that merely *starts* with a backticked token as a reason-code assertion —
including prose. Reproduced:

```markdown
| Case | Reason                                                  |
|------|---------------------------------------------------------|
| c1   | `pulldown-cmark` handles this correctly per CommonMark   |
```
```
probe-b.md:5: reason code 'pulldown-cmark' not in closed taxonomy (POLICY 19)
```

Note the in-code comment retained from the BLOCKING-3 repair (lines 342–347) still claims
long notes cells "are excluded … exactly as before" and specifically names
`` `pulldown-cmark` `` as a must-not-match. That is no longer true when the cell leads with
the backtick, so the comment now misdescribes the code.

Not blocking: no in-corpus instance exists (the corpus output is unchanged), the cell must
sit inside a *confirmed* Reason column, and the failure mode is fail-loud rather than
fail-silent. Consider requiring the annotation to start with an opening paren/bracket —
e.g. `` re.match(r"`([A-Za-z][a-zA-Z0-9-]{2,})`(?:\s*[([].*)?$", …) `` — which keeps 5i
green while re-excluding prose. At minimum, correct the comment.
