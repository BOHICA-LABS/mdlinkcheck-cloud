METHODOLOGY NOTE — WHY --no-fail-fast IS REQUIRED
All six runs below were executed with `cargo nextest run --no-fail-fast`.
Without this flag, nextest cancels the run after the first failure (fail-fast
is the default). A partial run such as "25/44 tests run: 22 passed, 3 failed"
is NOT a kill count — it is a floor from an aborted run. Only a complete run
("44 tests run") produces a trustworthy kill count. Every count in this matrix
comes from a 44-test complete run.

ASSERT-MUTANT-LANDED GUARD (L-90)
Each mutation was applied in an out-of-tree scratch copy
  (`git archive HEAD | tar -x -C <tmpdir>`)
with a `cmp` guard against the pristine file before compiling. If the file was
byte-identical to the pristine copy after the edit, the run was discarded. All
six guards below fired PASSED (the mutations landed).

PREVIOUS PUBLISHED COUNTS WERE WRONG — TWO ROOT CAUSES (BI-103)
The previously published table (6/2/10/2 for M1–M4) contained two errors:
1. FAIL-line double-counting: each failing test appeared twice in nextest output
   (once streamed during the run, once in the end-of-run recap). The old matrix
   counted FAIL lines, not distinct test names.
2. Fail-fast cancellation: all four killing runs stopped early. Their summaries
   read "25/44", "25/44", "21/44", "18/44" — aborted run floors, not complete
   counts. Two mutants that only fired in the tail of the test suite (M3's 6th
   and 7th kills) were invisible. M4's tail kill was also invisible but the
   doubling error happened to restore the correct number of 2.
